# 00. 요구사항과 설계 정합성

## 핵심 요구사항

| # | 요구사항 | 설계 대응 | 문서 |
|---|---|---|---|
| R1 | 결정론 단계와 Agent 판단 단계를 하나의 워크플로로 실행한다 | 노드 유형(Task · Agent · Human), 실행 루프, 공유 State | 05, 08 |
| R2 | 순차 · 조건 분기 · 병렬 분기와 합류 · 반복 · 다중 인스턴스 · 대기 · 하위 워크플로를 지원한다 | DSL Edge, 합류 카운터, Map 노드, 종료 조건 검증 | 05, 11 |
| R3 | 레거시 및 외부 시스템과 연계한다 | MCP gateway, Registry, Task executor | 08 |
| R4 | 운영 중 워크플로 변경이 진행 중인 실행에 영향을 주지 않는다 | IR 불변 버전, Run 버전 고정 | 04, 06 |
| R5 | 개발자가 아닌 사용자도 워크플로를 정의 · 수정할 수 있다 | DSL → IR 컴파일, 배포 전 검증, Policy | 04 |
| R6 | 사람의 승인 · 검토 단계를 포함하고, 장기간 대기할 수 있다 | Human executor, HITL service, Outbox | 09 |
| R7 | Agent의 무한 반복 · 토큰 과다 사용 · 권한 남용을 통제한다 | 루프 가드, 토큰 예산(예약 · 정산), 최소 권한 | 12 |
| R8 | 여러 Agent가 역할을 나누어 협업하고 결과를 상호 검토한다 | 공유 State, Router 종료 조건 | 05 |
| R9 | Agent의 판단 근거와 실행 이력을 추적하고 재현할 수 있다 | Checkpoint 이력, 반복 기록, Trace, Replay · Fork | 13 |
| R10 | 민감정보 유출과 프롬프트 공격에 대응한다 | Guardrail, 마스킹, 간접 인젝션 격리 | 13 |
| R11 | 장애가 발생해도 진행 중인 작업을 유실 없이 이어서 수행한다 | 임대 · 재전달, 반복 기록, 펜싱 토큰, 멱등키 | 10 |
| R12 | 구성요소 장애 시에도 서비스가 지속되고, 부하 증가 시 수평 확장된다 | 장애 대응 매트릭스, Stateless 구성, 큐 분리, 동시성 제한, 역압 | 11 |

## 확장 요구사항

핵심 설계의 확장 지점에 기능을 더하는 방식으로 수용합니다.

| # | 요구사항 | 변경 범위 | 문서 |
|---|---|---|---|
| E1 | 사용자가 처리 진행 상황을 실시간으로 확인한다 | 컴포넌트 추가 (SSE gateway) | 15 |
| E2 | 특정 LLM 장애나 모델 교체에도 서비스가 영향받지 않는다 | 기존 확장 (LLM gateway) | 14 |
| E3 | 워크플로 변경 시 품질 저하를 사전에 검증한다 | 기존 확장 (Evaluation) | 18 |
| E4 | Agent가 상황에 따라 처리 절차를 스스로 계획한다 | 노드 유형 추가 (Planner) | 16 |
| E5 | 과거 처리 이력과 사내 지식을 참고해 판단한다 | 컴포넌트 추가 + 기존 확장 (Memory service) | 17 |

범위 외: 조직 단위 관리(멀티테넌시, 조직별 비용 집계)

## 요구사항 해석
- R11은 인프라 장애(Worker 중단)와 논리적 실패(Agent 실패, 모델 장애)를 모두 포함한다.
- R7은 실행 통제(반복 · 토큰)와 권한 통제(최소 권한 · 승인)로 나누어 대응한다.
- R9의 재현은 기록 재생(동일 결과 확인)과 분기 재실행(조건을 바꿔 다시 실행)을 모두 의미한다.
- R2는 병렬을 정의하는 능력이고, R12는 정의된 병렬을 실제로 얼마나 동시에 실행하는가의 문제다.

## 공통 메커니즘

요구사항 대부분은 네 가지 메커니즘의 조합으로 충족됩니다.

| 메커니즘 | 관련 요구사항 |
|---|---|
| 중단 · 재개 (Checkpoint + Outbox) | R6, R9, R11, E1, E4 |
| Agent 통제 (실행기 검사 지점) | R7, R10, E5 |
| DSL → IR (Compiler + Policy) | R4, R5, E4 |
| 공유 State · 이벤트 기반 스케줄링 | R1, R2, R8, R12 |

## 설계 정합성 검토

요구사항 간 충돌 가능 지점과 해소 방법입니다. 모든 항목은 새로운 예외 규칙 없이 설계 불변식으로 해소됩니다.

| 관련 요구사항 | 충돌 가능성 | 해소 방법 | 불변식 |
|---|---|---|---|
| E4 동적 계획 ↔ R4 버전 독립 | 실행 중 그래프 변경 시 버전 고정이 깨짐 | 부모 그래프 불변, 새 계획은 자식 Run (생성 IR도 IR store에 저장) | I1, I7 |
| E4 동적 계획 ↔ R7 · R10 통제 · 보안 | Agent가 위험한 계획 생성 | 동일 Compiler 검증, 자식 권한 · 예산 ⊆ 부모, 쓰기 Tool 승인 자동 삽입 | I7, I8, I9 |
| E4 동적 계획 ↔ R11 장애 재개 | 자식 실행 중 장애 | 자식도 일반 Run과 동일한 재개 메커니즘, 부모는 Suspended로 대기 | I1, I2 |
| E4 동적 계획 ↔ Run 취소 | 부모 취소 시 자식이 남음 | 부모 취소 시 자식 연쇄 취소 | I1 |
| E5 기억 ↔ R9 재현 | 기억 저장소 변경으로 재생 결과가 달라짐 | 조회한 기억 ID · 내용을 반복 기록에 저장, 재생 시 재사용 | I6 |
| E5 기억 ↔ R10 보안 | 민감정보 · 악성 지시 축적 | 저장 전 마스킹 · 품질 게이트, 주입 시 데이터로 격리 | I5 |
| E5 기억 ↔ R11 장애 | 실패한 중간 판단이 저장됨 | 기억 저장은 Run 완료 후, 성공 · 승인 건 중심 | I3 |
| E1 실시간 ↔ R6 장기 대기 | 사용자의 장시간 대기 | 동기 대기 후 비동기 전환, SSE로 상태 확인 | I2 |
| E1 실시간 ↔ R10 보안 | 진행 이벤트로 민감정보 노출 | 진행 이벤트 마스킹, 구독 시 조회 권한 확인 | I5 |
| E1 실시간 ↔ R11 장애 | 재연결 시 이벤트 유실 | 상태 이벤트는 Event log에서 재생, 진행 이벤트는 유실 허용 | I3 |
| E2 모델 교체 ↔ R9 재현 | 폴백 모델이 다른 결과 생성 | 실제 모델 · 강등 여부 기록, 재생 시 기록값 사용 | I6 |
| E2 모델 교체 ↔ R10 보안 | 폴백으로 데이터 등급 우회 | 등급 필터는 폴백 시에도 유지, 안전 거부는 폴백 금지 | I5, I9 |
| R2 · R12 병렬 ↔ R7 토큰 예산 | 동시 호출로 예산 초과 | 예약 · 정산 방식의 원자적 차감 | I8 |
| R2 · R12 병렬 ↔ State 정합성 | 병렬 노드의 동일 필드 쓰기 | Map은 항목별 슬롯, 고정 분기는 reducer 선언 (미선언 시 Validator가 거부) | I2, I7 |
| R11 장애 재개 ↔ R7 토큰 예산 | 재생 시 비용 중복 | 재생 구간은 기록값 사용, 미정산 예약은 임대 만료 시 해제 | I6 |
| R6 HITL ↔ R7 토큰 예산 | 대기 중 예약이 묶임 | Suspended 시점에 미정산 예약 해제 | I3 |
| R6 HITL ↔ R4 버전 | 대기 중 새 버전 배포 | 대기 Run은 시작 버전 유지, 이전은 graph_hash 호환 시 명시적으로만 | I1 |
| R6 HITL ↔ R11 장애 | 승인 요청 중복 · 유실 | Outbox로 유실 방지, 요청 ID 중복 제거, 재개 토큰 1회용 | I3, I4 |
| R5 선언적 정의 ↔ R10 보안 | 작성자의 보안 설정 누락 | Policy 강제 규칙을 컴파일 시 주입 | I9 |
| R8 멀티 Agent ↔ R7 통제 | Agent 간 무한 반복 | 종료 판단은 코드(Router), 반복 · 예산 상한 | I8 |

### 검토를 통해 반영한 사항
1. 부모 Run 취소 시 자식 Run 연쇄 취소 (06)
2. Suspended 시점의 미정산 토큰 예약 해제 (12)
3. Map 항목 단위의 펜싱 토큰 · 멱등키 · 중복 제거 키에 항목 번호 포함 (10, 11)
4. SSE 구독 권한 확인 및 진행 이벤트 마스킹 (15)
5. 실행기 종료 상태를 문서와 코드에서 동일한 7종으로 정의 (08, 19)
